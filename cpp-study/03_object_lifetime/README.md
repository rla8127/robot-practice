## 2. 왜 이걸 배워야 하나?

Python에서는 객체를 언제 지울지 **GC(가비지 컬렉터)**가 알아서 정한다. "언젠가" 지워진다.

C++은 다르다. 객체가 사라지는 시점이 **코드에 정확히 정해져 있다.**
그리고 사라지는 순간 **소멸자(destructor)**가 반드시 호출된다.

장비 쪽에서 이게 왜 중요할까?

```
{
    MotorDriver driver;   // 생성자: 모터 전원 ON
    driver.move(...);
}                         // 소멸자: 모터 전원 OFF  ← 이 줄에서 "반드시" 실행된다
```

"블록이 끝나면 반드시 모터가 꺼진다"를 **언어가 보장**해 준다.
`off()`를 깜빡할 일이 없다. 이게 다음 장 RAII의 핵심 아이디어고, 오늘은 그 바탕이 되는 "시점 규칙"을 익힌다.

## 3. 꼭 외울 규칙 4개

| 객체 종류 | 생성 시점 | 소멸 시점 |
|---|---|---|
| 지역 변수 | 선언한 줄 | 그 변수가 속한 `{ }` 블록이 끝날 때 |
| 같은 블록의 여러 객체 | 선언 순서대로 | **역순**으로 (나중에 만든 것이 먼저 사라짐) |
| 클래스 멤버 | **클래스에 선언된 순서**대로 (생성자 본문보다 먼저) | 소멸자 본문이 끝난 **뒤**, 역순으로 |
| 전역 변수 | `main` 시작 **전** | `main` 끝난 **후** |
| (보너스) 이름 없는 임시 객체 | 그 문장 실행 중 | 그 문장의 `;`에서 바로 |

**왜 역순일까?** 접시 쌓기를 생각하면 된다. 맨 나중에 올린 접시를 먼저 내린다.
나중에 만든 객체는 먼저 만든 객체를 **쓰고 있을 수도** 있다. (예: 모터 제어기는 통신 포트를 쓴다)
그러니 쓰는 쪽(제어기)이 먼저 사라지고, 쓰이는 쪽(포트)이 나중에 사라져야 안전하다.

```
생성:  포트 → 제어기         (제어기가 포트를 씀)
소멸:  제어기 → 포트         (제어기가 다 쓰고 나서야 포트 닫기)
```

## 4. main.cpp 한 줄씩 읽기

### 4-1. Tracer: 태어나고 죽을 때 소리 내는 클래스

```cpp
class Tracer {
public:
    explicit Tracer(std::string name) : name_(std::move(name)) {
        std::cout << "  + 생성: " << name_ << '\n';
    }
    ~Tracer() {
        std::cout << "  - 소멸: " << name_ << '\n';
    }
private:
    std::string name_;
};
```

- `Tracer(std::string name)` : **생성자**. 만들어질 때 `+ 생성: 이름`을 출력한다.
- `~Tracer()` : **소멸자**. 이름 앞에 `~`(물결)를 붙인다. 사라질 때 `- 소멸: 이름`을 출력한다.
  - 소멸자는 인자도 반환값도 없고, **내가 직접 부르지 않는다.** 언어가 알아서 부른다.
- `std::move(name)` : 지금은 "받은 문자열을 복사하지 않고 `name_`으로 **옮겨 담는다**" 정도만 알면 된다.
  자세한 내용은 06장(복사 vs 이동)에서 배운다.

이 클래스는 기능이 없다. 오직 **"언제 생기고 언제 사라지나"를 눈으로 보기 위한 도구**다.

### 4-2. 블록과 역순 소멸

```cpp
Tracer a("a");
{
    std::cout << "[안쪽 블록 시작]\n";
    Tracer b("b");
    Tracer c("c");
    std::cout << "[안쪽 블록 끝]\n";
}  // ← 여기서 c, b 순서로 소멸
```

- `a`는 `main` 블록에 속한다 → `main`이 끝날 때까지 살아 있다.
- `b`, `c`는 안쪽 `{ }`에 속한다 → 닫는 `}`에서 사라진다. 순서는 **c 먼저, b 나중** (역순).
- 주목: `[안쪽 블록 끝]`이 출력된 **다음에** 소멸이 일어난다. 소멸은 `}` 줄에서 일어나기 때문이다.

`{ }`만 따로 써서 블록을 만드는 건 문법상 아무 문제 없다. "이 객체는 여기까지만 쓴다"를 표시하는 방법이다.

### 4-3. 클래스 멤버의 순서

```cpp
class Robot {
public:
    Robot() : motor_("Robot::motor_"), sensor_("Robot::sensor_") {
        std::cout << "  (Robot 생성자 본문 실행)\n";
    }
    ~Robot() {
        std::cout << "  (Robot 소멸자 본문 실행)\n";
    }
private:
    Tracer motor_;
    Tracer sensor_;
};
```

로봇은 모터와 센서를 **부품으로 가지고 있다.** 부품과 몸체의 순서가 핵심이다.

**생성할 때: 부품 먼저, 본문 나중**
```
motor_ 생성 → sensor_ 생성 → Robot 생성자 본문
```
생성자 본문 `{ }`이 실행될 때는 부품이 **이미 다 준비되어 있어야** 본문에서 부품을 쓸 수 있기 때문이다.

**소멸할 때: 본문 먼저, 부품 나중 (역순)**
```
Robot 소멸자 본문 → sensor_ 소멸 → motor_ 소멸
```
소멸자 본문에서 "모터 정지" 같은 정리 작업을 하려면 그때까지 부품이 **살아 있어야** 하기 때문이다.

**초기화 리스트(`: motor_(...), sensor_(...)`)란?**
생성자 이름 뒤 `:`부터 `{` 앞까지. 멤버를 **만드는 순간** 어떤 값으로 만들지 정한다.
Tracer는 기본 생성자가 없어서(이름이 꼭 필요해서) 여기서 이름을 줘야만 만들 수 있다.

**함정:** 멤버가 만들어지는 순서는 초기화 리스트에 **쓴 순서가 아니라**, 클래스 안에 **선언된 순서**(`motor_` → `sensor_`)다. 해 보기 2에서 확인한다.

### 4-4. 전역 객체

```cpp
Tracer g_global("전역 객체");
```

함수 밖에 선언한 변수. `main`이 시작되기 **전에** 생성되고, `main`이 끝난 **후에** 소멸한다.
그래서 출력의 **맨 처음과 맨 끝**에 나온다.

`g_` 접두사는 "global(전역)"이라는 표시 관례다. 전역 객체는 생성 순서를 제어하기 어려워서 실무에서는 **되도록 쓰지 않는다.**

### 4-5. 이름 없는 임시 객체

```cpp
Tracer("임시");  // 이름 없는 임시 객체
std::cout << "  (임시 객체 다음 줄)\n";
```

변수 이름 없이 만들면 **그 문장이 끝나는 `;`에서 바로** 사라진다.
그래서 `생성: 임시` 바로 다음에 `소멸: 임시`가 나오고, 그다음에야 `(임시 객체 다음 줄)`이 나온다.

01의 Q2에서 `startMotor(3)`이 "임시 Motor를 만들어서 넘긴다"고 했던 것, 기억나나?
그 임시 Motor도 이렇게 **문장이 끝나면 바로 사라지는** 객체였다.

### 해 보기 3: new로 만들고 delete를 잊으면? (10분) — 연습 과제 3번

`main()` 안에 추가한다.

```cpp
std::cout << "[new로 생성]\n";
Tracer* leaked = new Tracer("new로 만든 것");
```

1. 실행해서 출력 끝까지 본다. `- 소멸: new로 만든 것`이 **나오나?**
2. `[main 끝]` 앞에 `delete leaked;`를 추가하고 다시 실행한다. 이번엔 어디서 소멸이 나오나?

- `new`로 만든 객체는 블록이 끝나도 **사라지지 않는다.** 내가 `delete`를 불러야만 사라진다.
- `delete`를 잊으면 소멸자가 **영영 호출되지 않는다.** 메모리가 새는 것(메모리 누수, memory leak)뿐 아니라,
  소멸자에서 하기로 한 일(모터 끄기, 파일 닫기)도 **안 일어난다.**

> 프로그램이 끝나면 OS가 메모리는 회수해 준다. 하지만 **소멸자는 실행되지 않는다.**
> 메모리보다 "정리 작업이 안 일어났다"는 게 장비 쪽에서는 더 무서운 문제다.

이 문제를 해결하는 방법이 바로 04 RAII와 05 스마트 포인터다.
학습 가이드의 Phase 1 완료 기준이 **"new/delete 없이 소유권 관리"**인 이유가 여기 있다.

### 해 보기 4: 02의 위험한 참조, 다시 보기 (10분)

02의 해 보기 5에서 본 코드를 Tracer로 바꿔서 생각해 본다. (실행하지 않고 머리로만)

```cpp
Tracer& makeTracer() {
    Tracer t("함수 안의 t");
    return t;
}

int main() {
    Tracer& ref = makeTracer();
    // ref를 여기서 쓰면?
}
```

1. `t`의 소멸자는 어느 줄에서 호출되나? (3절 규칙표의 "지역 변수" 줄)
2. 그럼 `ref`는 **이미 소멸한** 객체의 별명이다. 이런 참조를 **댕글링 참조(dangling reference)**라고 한다.
3. 02 해 보기 5의 질문 "돌려받은 별명은 무엇의 별명인가?"에 이제 답할 수 있나?

> 댕글링 참조는 **컴파일은 되고**(경고만 나옴), 실행하면 어떤 때는 멀쩡해 보이고 어떤 때는 이상한 값이 나온다.
> 그래서 찾기 아주 어려운 버그다. **"참조/포인터는 원본보다 오래 살면 안 된다"**를 기억하자.
